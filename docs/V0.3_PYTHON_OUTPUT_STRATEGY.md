# V0.3 Python 输出策略说明

## 1. 这次改造解决什么问题

原来的采集任务在拿到 Tushare 日线数据后，直接调用 `StockRepository` 写入 MySQL。现在采集逻辑与输出方式已经拆开，同一套采集任务可以通过环境变量选择：

- `mysql`：只写 MySQL，保持 V0.2 的默认行为。
- `kafka`：只发送 Kafka 事件，不写 MySQL。
- `dual`：MySQL 和 Kafka 都执行，用于迁移期双写核对。

配置位置：项目根目录 `.env`。

```env
COLLECTOR_OUTPUT_MODE=mysql
```

可选值只能是 `mysql`、`kafka`、`dual`。配置错误时程序会在启动阶段直接报错，避免任务运行到中途才发现输出模式无效。

## 2. 完整调用链

```text
TushareCollector
    -> DailyCollectionJob
    -> DataFrame 校验
    -> DailyOutputBatchFactory
       -> records（给 MySQL）
       -> StockDailyEvent（给 Kafka）
    -> OutputFactory
       -> MysqlOutput
       -> KafkaOutput
       -> DualOutput
    -> TaskRepository 更新最终状态
```

`HistoryBackfillJob` 和 `RetryFailedJob` 仍然复用 `DailyCollectionJob`，并把同一个输出策略传进去，所以历史回补和失败重试也会遵守 `COLLECTOR_OUTPUT_MODE`。

## 3. 关键类的职责

### DailyOutputBatchFactory

输入采集器返回的字典列表，输出一个 `DailyOutputBatch`：

- `records` 保留数据库字段格式，并补充数据源。
- `events` 转换成 Kafka 的 `StockDailyEvent`。
- 同一次任务中的事件共享一个 `traceId`。
- `eventId` 只由数据源、股票代码、交易日决定，因此重试时保持稳定。
- 不修改采集器传入的原始字典，避免 MySQL 与 Kafka 互相影响。

### MysqlOutput

调用 `StockRepository.save_daily_records()`，把数据库写入数量转换成统一的 `OutputResult`。数据库异常不会直接泄漏到任务编排层，而是转换成失败结果和错误信息。

### KafkaOutput

逐条发送事件，最后只 `flush` 一次。结果只统计当前批次，不会把以前批次的成功或失败误算进来。

### DualOutput

MySQL 和 Kafka 都会执行。即使第一个输出抛出异常，第二个输出仍会继续，避免因为一个系统故障完全丢失另一条可用链路。

双写结果会保留两个子结果：

```python
result.details["MYSQL"]
result.details["KAFKA"]
```

### OutputFactory

根据输出模式组装对象。`mysql` 模式不会初始化 Kafka Producer；只有 `kafka` 和 `dual` 模式才连接 Kafka。

## 4. 任务状态规则

| 输出情况 | 任务状态 | 含义 |
|---|---|---|
| 所有配置输出成功 | `SUCCESS` | 本次任务完整完成 |
| 双写时只有一个输出成功 | `PARTIAL_SUCCESS` | 数据至少到达一个目标，需要后续重试 |
| 所有配置输出失败 | `FAILED` | 本次任务没有完成 |

`TaskRepository.get_failed_tasks()` 会同时查询 `FAILED` 和 `PARTIAL_SUCCESS`，因此失败重试任务可以继续修复双写不一致。

MySQL 使用 `INSERT IGNORE`，Kafka 的 `eventId` 保持稳定，所以重试具备业务幂等基础。Kafka 下游仍应以 `eventId` 做去重。

## 5. 常用运行方式

只写 MySQL：

```env
COLLECTOR_OUTPUT_MODE=mysql
```

只写 Kafka：

```env
COLLECTOR_OUTPUT_MODE=kafka
```

迁移期双写：

```env
COLLECTOR_OUTPUT_MODE=dual
```

修改 `.env` 后重新执行任务：

```powershell
D:\Python\python.exe -m app.main daily --date 20260807
```

运行 Python 全量测试：

```powershell
D:\Python\python.exe -m pytest -q
```

查看 Kafka Topic：

```powershell
docker compose -f infrastructure\docker-compose.yml exec kafka /opt/kafka/bin/kafka-topics.sh --bootstrap-server localhost:9092 --list
```

Kafka UI：`http://localhost:8081/`。

## 6. 推荐迁移顺序

1. 先保持 `mysql`，验证原有采集任务没有回归。
2. 切到 `dual`，对比 MySQL 行数、Kafka 消息数和任务状态。
3. Java 消费端稳定后，再评估是否切换到 `kafka`。
4. 在完全取消 MySQL 直写前，保留 `dual` 一段观察期和可回滚配置。

回滚不需要改代码，只需把 `.env` 中的 `COLLECTOR_OUTPUT_MODE` 改回 `mysql`。
