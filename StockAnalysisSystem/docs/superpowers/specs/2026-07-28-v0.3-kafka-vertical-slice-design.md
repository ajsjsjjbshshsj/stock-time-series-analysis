# V0.3 Kafka 纵向链路迁移设计

## 1. 目标

本阶段在保留 V0.2 Python 独立采集服务及其 MySQL 行为不变的前提下，完成第一条可运行的跨语言消息链路：

```text
Python 固定测试事件
  → Kafka
  → Java Spring Boot Consumer
  → JSON 反序列化
  → 协议校验
  → 错误隔离与消费统计
```

本阶段用于尽早验证 Python、Kafka 和 Java 之间的协议兼容性。真实行情采集 Job、MySQL/Kafka 双写、交付状态表及精确失败重试留给后续 V0.3 阶段。

## 2. 范围

### 2.1 本阶段包含

- 将工程统一整理到 `StockAnalysisSystem` 根目录下。
- 使用 Docker Compose 部署单节点 KRaft Kafka 和 Kafka UI。
- 创建 `stock.ods.daily.v1`、`stock.ods.basic.v1` 和 `stock.dead-letter.v1` 三个 Topic。
- 定义 V1 `StockDailyEvent` 跨语言消息协议。
- Python 增加事件生成、JSON 序列化、Kafka Producer 和固定消息发送入口。
- Java 建立 Maven 多模块工程，包含可复用的 `common-model` 和独立 Consumer 服务。
- Java Consumer 完成日线消息反序列化、基础协议校验、异常隔离、DLQ 投递和线程安全统计。
- 提供消费统计、最近错误和健康检查接口。
- 增加 Python、Java 单元测试和 Docker 联调测试。

### 2.2 本阶段不包含

- 不修改 `DailyCollectionJob`、`HistoryBackfillJob` 或 `RetryFailedJob`。
- 不增加 `mysql`、`kafka`、`dual` 三种真实采集输出模式。
- 不增加 `collection_delivery` 数据库表。
- Java Consumer 不写 MySQL、ClickHouse 或 Redis。
- 不实现指标计算、复杂行情清洗、有状态去重或窗口计算。
- 不引入 Flink、Spark、Iceberg、MinIO、Airflow 或模型训练消息化。
- `stock.ods.basic.v1` 本阶段只创建 Topic，不接入真实基础信息采集。

## 4. 架构边界

### 4.1 Python

Python 负责：

- 构造确定性的固定日线测试数据。
- 生成 `StockDailyEvent`。
- 将内部 snake_case 模型序列化为 camelCase UTF-8 JSON。
- 使用 `tsCode` 作为 Kafka Key。
- 异步生产消息、处理 delivery callback、执行 flush，并输出成功与失败数量。

本阶段 Python Producer 不由真实 Collector 或 Job 调用。

### 4.2 Kafka

Kafka 是 Python 与 Java 之间唯一的运行时边界。双方不得直接引用或调用对方代码。

Topic 设计：

| Topic | 分区数 | 用途 |
|---|---:|---|
| `stock.ods.daily.v1` | 3 | V1 日线原始事件 |
| `stock.ods.basic.v1` | 1 | 预留的 V1 股票基础信息事件 |
| `stock.dead-letter.v1` | 1 | 无法正常解析或校验的原始消息 |

Kafka 只承担消息传输，不作为永久历史数据库。

### 4.3 Java common-model

`common-model` 只保存跨模块可复用的协议类型，不依赖 Spring Web、数据库驱动或 Consumer 业务实现。V0.4 Flink 模块可以直接复用该模块的事件类型。

### 4.4 Java Consumer

Java Consumer 负责：

- 接收 `ConsumerRecord<String, String>`。
- 使用 Jackson 将 JSON 反序列化为 `StockDailyEvent`。
- 校验协议版本、必要字段、Kafka Key 和基础数值合理性。
- 对成功和不同失败类型进行线程安全计数。
- 保存有容量上限的最近错误摘要。
- 将异常原始消息尽力发送到 DLQ。
- 无论单条消息成功或被隔离，均继续消费后续消息。

## 5. StockDailyEvent V1 协议

Kafka Value 使用 UTF-8 JSON，字段名统一使用 camelCase。

| JSON 字段 | Java 类型 | JSON 表示 | 规则 |
|---|---|---|---|
| `eventId` | `String` | string | `{SOURCE}:{tsCode}:{yyyyMMdd}` |
| `traceId` | `String` | string | `smoke-{source}-{yyyyMMdd}-{runId}` |
| `tsCode` | `String` | string | 必填，同时作为 Kafka Key |
| `tradeDate` | `LocalDate` | ISO date | 例如 `2026-07-03` |
| `open` | `BigDecimal` | number | 可空，不经过二进制浮点转换 |
| `high` | `BigDecimal` | number | 可空，不经过二进制浮点转换 |
| `low` | `BigDecimal` | number | 可空，不经过二进制浮点转换 |
| `close` | `BigDecimal` | number | 可空；非空时不得小于 0 |
| `preClose` | `BigDecimal` | number | 可空 |
| `change` | `BigDecimal` | number | 可空 |
| `pctChg` | `BigDecimal` | number | 可空 |
| `volume` | `BigDecimal` | number | 可空；非空时不得小于 0 |
| `amount` | `BigDecimal` | number | 可空；非空时不得小于 0 |
| `source` | `String` | string | 必填，固定使用大写数据源名 |
| `eventTime` | `OffsetDateTime` | ISO offset datetime | 日线使用交易日 15:00:00，偏移 `+08:00` |
| `ingestTime` | `OffsetDateTime` | ISO offset datetime | Producer 生成事件的实际时间 |
| `schemaVersion` | `Integer` | integer | 必填，本阶段固定为 `1` |

### 5.1 eventId

`eventId` 由数据源、股票代码和交易日期确定。例如：

```text
TUSHARE:000001.SZ:20260703
```

重复生成相同业务事件时 `eventId` 必须保持一致，不允许使用随机 UUID。

### 5.2 traceId

固定消息发送命令的一次执行共享同一个 `traceId`。格式为：

```text
smoke-{source}-{businessDate}-{runId}
```

`runId` 标识本次测试执行，不参与 `eventId` 计算。

### 5.3 Kafka Key

日线 Topic 的 Key 必须等于事件的 `tsCode`。Java Consumer 必须同时验证 Key 非空且与 Value 中的 `tsCode` 一致。

## 6. Python 组件设计

```text
app/events/stock_daily_event.py
app/events/event_factory.py
app/kafka/serializer.py
app/kafka/delivery_callback.py
app/kafka/producer.py
app/kafka/smoke_producer.py
```

- `StockDailyEvent` 使用 `Decimal`、`date` 和带时区的 `datetime`，避免在事件模型中使用价格浮点数。
- `EventFactory` 将固定业务记录转换为协议事件并统一生成 `eventId`、`traceId`、`eventTime` 和 `ingestTime`。
- Serializer 负责 camelCase 映射以及 Decimal、日期和带偏移时间的 JSON 表示。
- Producer 封装 Kafka 客户端，支持异步发送、delivery callback、成功/失败计数、flush 和 close。
- `smoke_producer` 是独立 CLI，只发送确定性测试数据，不加载数据库密码或 Tushare Token。

Producer 核心配置：

```text
acks=all
enable.idempotence=true
compression.type=lz4
```

固定消息命令至少支持：

```powershell
python -m app.kafka.smoke_producer --count 1
python -m app.kafka.smoke_producer --count 20
```

## 7. Java 组件设计

### 7.1 Maven 模块

```text
java-services/
├── pom.xml
├── common-model/
└── kafka-consumer-service/
```

- 父工程统一 Java 21、依赖管理和插件配置。
- `common-model` 包含 `StockDailyEvent`，只依赖 Jackson 注解及时间支持所需的轻量模块。
- Consumer 模块依赖 `common-model`、Spring for Apache Kafka、Spring Web、Validation、Actuator 和测试依赖。

### 7.2 Consumer 流程

```text
接收原始 ConsumerRecord
  → 增加 totalConsumed
  → Jackson 反序列化
  → StockEventValidator 校验
  → 增加成功与 dailyEventCount
  → 确认 offset
```

错误流程：

```text
反序列化或校验失败
  → 分类统计
  → 保存错误上下文摘要
  → 尝试投递 DLQ
  → 确认原消息 offset
  → 继续消费
```

## 8. 校验规则

必须校验：

- `eventId`、`traceId`、`tsCode`、`tradeDate`、`source` 和 `schemaVersion` 非空。
- `schemaVersion == supportedSchemaVersion`。
- Kafka Key 非空且等于 `tsCode`。
- `close`、`volume` 和 `amount` 非空时不得小于 0。

本阶段不校验 OHLC 复杂关系，不执行状态去重。

## 9. 异常隔离和 DLQ

失败分类至少包括：

- JSON 语法或字段类型错误。
- `LocalDate` 或 `OffsetDateTime` 解析错误。
- 必要字段缺失。
- 不支持的 `schemaVersion`。
- Kafka Key 与 `tsCode` 不一致。
- DLQ 投递失败。

错误记录保留：

```text
timestamp
errorType
message
key
topic
partition
offset
```

最近错误列表使用固定容量，避免长期运行时无限增长。日志和接口不得输出环境变量、Token、数据库密码或完整敏感配置。

DLQ 投递是尽力而为。DLQ 暂时不可用时记录独立错误和计数，但不能让原 Consumer 因毒消息永久阻塞。

## 10. 消费统计与接口

线程安全统计至少包含：

```text
totalConsumed
successCount
failureCount
dailyEventCount
basicEventCount
jsonParseFailureCount
validationFailureCount
unsupportedSchemaCount
dlqPublishFailureCount
lastConsumedTime
```

接口：

```text
GET /api/consumer/statistics
GET /api/consumer/errors
GET /actuator/health
```

这些接口只用于开发联调、监控和演示，不承担股票查询业务。

## 11. 配置

统一环境变量：

```text
KAFKA_BOOTSTRAP_SERVERS=localhost:9092
KAFKA_CLIENT_ID=stock-python-collector-v1
KAFKA_CONSUMER_GROUP_ID=stock-java-validation-consumer-v1
KAFKA_DAILY_TOPIC=stock.ods.daily.v1
KAFKA_BASIC_TOPIC=stock.ods.basic.v1
KAFKA_DLQ_TOPIC=stock.dead-letter.v1

```

Python Producer 还支持：

```text
KAFKA_ACKS=all
KAFKA_COMPRESSION_TYPE=lz4
KAFKA_LINGER_MS
KAFKA_MESSAGE_TIMEOUT_MS
```

`.env.example` 只写示例值，不写真实 Token 或密码。

## 12. 测试设计

### 12.1 Python 单元测试

- 同一 source、tsCode、tradeDate 生成稳定 `eventId`。
- 一次发送使用统一 `traceId`。
- JSON 字段为 camelCase。
- Decimal 输出为 JSON number 且精度不经过 float。
- `tradeDate`、`eventTime` 和 `ingestTime` 格式正确。
- Producer 使用 `tsCode` 作为 Key。
- delivery callback 正确增加成功和失败计数。
- flush 失败时命令返回失败且抛出明确异常。

### 12.2 Java 单元测试

- Python 格式 JSON 可反序列化为 `StockDailyEvent`。
- `LocalDate`、`OffsetDateTime` 和 `BigDecimal` 类型正确。
- 必填字段、版本、Kafka Key 和非负数校验正确。
- JSON 解析错误和协议错误分类正确。
- 并发更新统计时不丢计数。
- 最近错误列表遵守容量限制。

### 12.3 Docker 集成测试

依次验证：

1. Kafka、Kafka UI 和三个 Topic 可用。
2. Python 发送 1 条消息，Java 成功计数增加 1。
3. Python 发送 20 条消息，Java 成功增量与 Python 成功发送数一致。
4. 发送错误 JSON，Consumer 不退出且 JSON 失败数增加。
5. 发送不支持的版本，Consumer 不退出且版本失败数增加。
6. 发送错误 Key，Consumer 不退出且校验失败数增加。
7. 失败消息能够进入 DLQ；若 DLQ 投递失败，则独立失败计数增加。

## 13. 验收标准

- Docker Compose 可以启动 Kafka 和 Kafka UI。
- 三个规定 Topic 均存在且分区数正确。
- Python 可以发送 1 条和 20 条固定日线事件。
- Kafka Key 始终等于 `tsCode`。
- `eventId` 对相同业务记录保持稳定。
- Java 可以正确解析日期、时区和高精度数值。
- Java 成功消费增量与 Python 成功发送数一致。
- 错误消息不会终止 Consumer，并可在统计和最近错误接口中观察。
- Actuator 健康检查可访问。
- V0.2 Collector、Job、Repository、MySQL 配置和原有测试行为没有被改变。

## 14. 回滚

本阶段没有接入真实采集 Job，因此回滚只需：

1. 停止 Java Consumer。
2. 停止 Kafka Compose 环境。
3. 不执行固定消息 Producer。

V0.2 的 `Python Collector → MySQL` 链路不依赖本阶段新增组件，不需要修改配置即可继续运行。
