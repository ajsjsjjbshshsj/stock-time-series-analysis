# V0.5 Flink 端到端验收

在 `StockAnalysisSystem` 目录执行。需要已启动的 Kafka/Flink Compose 栈、已创建的 V0.5 topics、一个运行中的 `stock-daily-indicator-v1` 作业，以及包含 `confluent-kafka`、`simplejson` 的 Python 环境。脚本会通过 Flink REST API 自动发现唯一运行中的作业；也可传 `--job-id`、`--flink-url`、`--bootstrap-servers` 和各 topic 参数。所有场景有界等待（默认 180 秒），不匹配时退出码为 1。输出只统计本次 UUID 派生的股票代码；每个消费者使用新的 group ID 和 `read_committed`。

## 自动验收步骤

```powershell
D:\Python\python.exe -m pytest python-services\python-collector\tests\test_verify_v05_flink.py -v
D:\Python\python.exe scripts\verify_v05_flink.py --scenario valid
D:\Python\python.exe scripts\verify_v05_flink.py --scenario late
D:\Python\python.exe scripts\verify_v05_flink.py --scenario invalid
D:\Python\python.exe scripts\verify_v05_flink.py --scenario recovery-before
docker restart stock-flink-taskmanager
docker compose -f infrastructure\docker-compose.yml ps
D:\Python\python.exe scripts\verify_v05_flink.py --scenario recovery-after
```

只在 `recovery-before` 返回 `PASS` 且写出 `StockAnalysisSystem/.tmp/v05-recovery.json` 后重启 TaskManager。不要删除该清单、Kafka topics/volumes 或 Flink checkpoints，也不要 `down -v` 或取消作业。清单已存在时，`recovery-before` 会拒绝覆盖；应先完成对应的 `recovery-after`，再由操作者决定如何保留旧证据。TaskManager 重启是唯一必要的扰动，`recovery-after` 会等待原 Job ID 和三个 slot 恢复。

## 验收断言

| 场景 | 输入与期望 |
| --- | --- |
| `valid` | 两只唯一股票各 D1–D20；每条主输出的 Kafka key、完整 JSON 字段、源事件 ID、六位小数、MA5/10/20、成交量均线、量比、窗口大小和预热标志与独立 Decimal/HALF_UP 计算一致。同日 D20 覆盖产生第二条同业务 `eventId`，但窗口仍为 20；本次股票不进入 late/DLT。 |
| `late` | D1–D20 后发送更旧的 D19；late topic 恰有一条，包含原事件、最新日期和原因；此时主 topic 没有新输出。随后覆盖 D20，核对均线与窗口以证明旧事件未污染状态。 |
| `invalid` | 发送损坏 JSON 和 Kafka key/`tsCode` 不一致的有效 JSON；Flink DLT 恰有两条，`originalKey`、`originalPayload`、来源 topic/partition/offset、`JSON_PARSE` 或 `KEY_MISMATCH` 完整保留，主 topic 无输出。 |
| `recovery-before` | 提交 D1–D10，确认十条唯一已提交输出；等待完成的 checkpoint，将 Job ID、checkpoint ID、股票代码和十个 `eventId` 保存到 `.tmp/v05-recovery.json`。 |
| `recovery-after` | TaskManager 重启后提交 D11–D20；新 `read_committed` 消费组从头读取本次股票，要求每个日期/业务 ID 恰好出现一次，全部字段和 D20 MA20 正确，无额外已提交输出，且完成的 checkpoint ID 大于重启前记录。作业保持 `RUNNING`。 |

主输出的业务 `eventId` 是 `tsCode + tradeDate` 的确定性 ID；因此 `valid` 中的主动同日覆盖会合法地重复该 ID。恢复场景没有覆盖，任何重复的已提交 `eventId` 都是失败。

若某场景失败，保留脚本 JSON 输出、恢复清单、Flink Job ID 与 checkpoint 记录，先定位原因；不要为了使测试通过而清理 topics、重置消费组或更改验证标准。
