# V0.2 数据采集服务化改造方案

## 1. 版本定位

V0.2 的核心目标不是引入 Kafka、Flink、Redis 或 ClickHouse，而是将原项目中的股票数据采集功能从主项目中拆分出来，形成一个可以独立运行、独立维护、独立测试的数据采集服务。

V0.2 完成后，数据采集服务仍然将行情数据写入 MySQL。Kafka 消息化将在 V0.3 中完成。

---

## 2. 当前项目存在的问题

当前项目中的数据采集、数据清洗、数据库写入、特征计算、模型训练和页面展示可能存在一定程度的耦合。

典型调用关系如下：

```text
主程序或 Dashboard
        ↓
调用数据采集代码
        ↓
调用 Tushare / AkShare
        ↓
简单处理数据
        ↓
直接写入 MySQL
        ↓
继续计算特征或训练模型
```

这种结构存在以下问题：

1. 采集功能无法独立运行；
2. 采集失败后不方便单独重试；
3. 历史数据回补流程不清晰；
4. 数据源调用逻辑与数据库写入逻辑耦合；
5. 采集任务缺少统一的状态记录；
6. 后续接入 Kafka 时改动范围较大；
7. Dashboard、模型训练等模块可能间接依赖采集代码；
8. 不方便为采集模块编写独立测试。

---

## 3. 改造思想

V0.2 的核心思想可以概括为：

> 将数据采集功能从“大项目中的一个模块”，改造成“一个职责单一的独立 Python 服务”。

改造前：

```text
StockAnalysisSystem
├── 数据采集
├── 数据清洗
├── 特征计算
├── 模型训练
└── 页面展示
```

改造后：

```text
StockAnalysisSystem
├── 主分析系统
│   ├── 数据清洗
│   ├── 特征计算
│   ├── 模型训练
│   └── 页面展示
│
└── Python Collector Service
    ├── Tushare 数据采集
    ├── AkShare 数据采集
    ├── 历史数据回补
    ├── 失败任务重试
    ├── 采集任务状态记录
    └── MySQL 数据写入
```

V0.2 只解决采集模块的独立性、可维护性和可追踪性，不改变整体技术架构。

---

## 4. V0.2 的主要目标

V0.2 需要实现以下目标：

1. 数据采集服务能够独立启动；
2. Tushare 和 AkShare 使用统一的采集接口；
3. 采集流程与数据库写入逻辑分离；
4. 支持指定交易日采集；
5. 支持指定日期范围的历史回补；
6. 支持失败任务重新执行；
7. 支持接口调用失败重试；
8. 记录每次采集任务的执行状态；
9. 避免重复采集产生无效重复数据；
10. 保持原有特征、模型和 Dashboard 功能不受影响。

---


## 7. 各模块职责

### 7.1 `main.py`

`main.py` 是采集服务的统一入口。

它负责：

1. 解析命令行参数；
2. 判断执行哪种采集任务；
3. 创建对应 Job；
4. 返回任务执行结果；
5. 设置程序退出状态。

建议支持以下操作：

```text
daily          采集指定交易日数据
history        回补指定日期范围数据
basic          更新股票基础信息
retry-failed   重试失败任务
```

示例运行方式：

```bash
python main.py daily --date 2026-07-03
python main.py history --start 2026-01-01 --end 2026-07-03
python main.py basic
python main.py retry-failed
```

### 7.2 `collectors/`

`collectors` 只负责调用外部数据源并返回统一格式的数据。

它不负责：

1. 写数据库；
2. 更新任务状态；
3. 计算技术指标；
4. 训练模型；
5. 操作 Dashboard。

推荐结构：

```text
BaseCollector
├── TushareCollector
└── AkShareCollector
```

#### `base_collector.py`

定义统一接口，例如：

```text
collect_daily(trade_date)
collect_basic()
collect_trade_calendar()
```

#### `tushare_collector.py`

负责：

1. 初始化 Tushare 客户端；
2. 调用 Tushare 接口；
3. 处理接口字段差异；
4. 返回统一字段的数据；
5. 处理空结果和接口异常。

#### `akshare_collector.py`

负责：

1. 调用 AkShare 接口；
2. 将 AkShare 字段转换为统一字段；
3. 返回与 TushareCollector 相同的数据格式；
4. 在必要时作为备用数据源。

### 7.3 `jobs/`

`jobs` 负责编排一个完整的采集任务。

它负责：

1. 创建采集任务记录；
2. 将任务状态更新为 `RUNNING`；
3. 调用 Collector；
4. 检查返回数据；
5. 调用 Repository 写入数据库；
6. 更新采集数量；
7. 将任务状态更新为 `SUCCESS`；
8. 捕获异常；
9. 失败时记录错误并更新为 `FAILED`。

#### `daily_collection_job.py`

处理单个交易日的数据采集。

```text
接收交易日期
    ↓
判断是否为交易日
    ↓
创建任务记录
    ↓
调用数据源采集
    ↓
检查返回结果
    ↓
写入 stock_daily
    ↓
更新任务状态
```

#### `history_backfill_job.py`

负责历史数据回补。

```text
接收开始日期和结束日期
    ↓
获取期间内所有交易日
    ↓
按交易日逐日调用 DailyCollectionJob
    ↓
记录每一天的执行结果
    ↓
输出成功数量和失败数量
```

#### `retry_failed_job.py`

负责读取失败任务，并重新执行对应采集流程。

### 7.4 `repositories/`

`repositories` 只负责数据库读写。

#### `stock_repository.py`

负责：

1. 写入股票基础信息；
2. 写入日线行情；
3. 批量插入数据；
4. 根据业务键处理重复数据；
5. 查询某个交易日是否已有数据。

建议业务唯一键：

```text
ts_code + trade_date
```

#### `task_repository.py`

负责：

1. 创建采集任务；
2. 更新任务状态；
3. 更新采集行数；
4. 记录失败原因；
5. 查询失败任务；
6. 判断任务是否已经成功执行。

Repository 不负责调用 Tushare，也不负责任务流程判断。

### 7.5 `models/`

建议至少包括：

```text
StockDaily
CollectionTask
```

`StockDaily` 用于统一 Tushare 和 AkShare 返回的字段。

建议字段：

```text
ts_code
trade_date
open
high
low
close
pre_close
change
pct_chg
volume
amount
source
created_at
updated_at
```

### 7.6 `utils/`

#### `logger.py`

统一日志格式和输出位置。

日志至少记录：

```text
任务类型
交易日期
数据源
重试次数
采集数量
运行耗时
失败原因
```

#### `retry.py`

统一接口重试策略。

建议重试范围：

```text
网络超时
临时连接错误
接口限流
数据源临时不可用
```

不建议对以下错误无限重试：

```text
Token无效
参数错误
字段结构错误
数据库表不存在
```

#### `date_utils.py`

负责：

```text
日期格式转换
交易日判断
日期范围生成
时区处理
```

## 9. 数据采集流程

### 9.1 单日采集流程

```text
用户或脚本发起单日采集
        ↓
main.py 解析参数
        ↓
DailyCollectionJob
        ↓
检查任务是否已成功执行
        ↓
创建或更新 collection_task
        ↓
调用 TushareCollector
        ↓
返回统一格式 DataFrame
        ↓
检查空数据和字段完整性
        ↓
StockRepository 批量写 MySQL
        ↓
更新任务状态为 SUCCESS
```

失败流程：

```text
调用数据源失败
        ↓
按照重试策略重试
        ↓
仍然失败
        ↓
任务状态改为 FAILED
        ↓
记录错误原因和重试次数
```

### 9.2 历史回补流程

```text
接收开始日期和结束日期
        ↓
查询交易日历
        ↓
生成需要采集的交易日列表
        ↓
逐日执行 DailyCollectionJob
        ↓
跳过已成功日期
        ↓
执行失败的日期单独记录
        ↓
输出回补任务汇总
```

回补任务不能因为某一天失败而直接停止整个流程。

建议最后输出：

```text
计划交易日数量
成功数量
失败数量
跳过数量
总写入行数
总耗时
```

### 9.3 失败重试流程

```text
查询 collection_task 中 FAILED 任务
        ↓
按照日期和数据源重新执行
        ↓
成功后更新为 SUCCESS
        ↓
失败时增加 retry_count
        ↓
保留最新错误信息
```

需要设置最大重试次数，避免错误任务无限循环。

```text
COLLECTOR_SOURCE=tushare
```

可选值：


后续可以扩展成：

```text
primary_source=tushare

```

V0.2 第一阶段不必实现复杂自动切换，可以先做到通过配置手动选择。

## 11. 数据幂等设计

数据幂等的目标是：

> 同一天的数据重复采集，不应产生多条重复行情记录。

建议使用以下业务键：

```text
ts_code + trade_date
```

写入方式可以选择：

1. 数据库唯一约束；
2. 插入前查询；
3. `INSERT ... ON DUPLICATE KEY UPDATE`；
4. 删除目标日期后重新批量写入。

推荐优先使用数据库唯一约束配合批量 Upsert。

任务状态和行情数据的幂等是两个不同问题：

```text
collection_task
    使用 task_type + business_date + source

stock_daily
    使用 ts_code + trade_date
```

## 12. 异常处理设计

### 可重试异常

```text
网络连接超时
远程服务临时不可用
接口限流
数据库临时连接失败
```

### 不可重试异常

```text
Token无效
请求参数错误
返回字段缺失
数据库表结构错误
配置缺失
```

### 空数据处理

空数据不应直接等同于成功。

需要判断：

1. 当天是否为交易日；
2. 数据源是否正常返回；
3. 返回字段是否完整；
4. 是否确实没有行情数据。

对于正常非交易日，可以记录为跳过；对于交易日返回空数据，应记录异常或警告。

## 13. 测试范围

### Collector 测试

1. 数据源正常返回时字段正确；
2. 返回空数据时能够识别；
3. 网络异常时能够重试；
4. Tushare 和 AkShare 返回统一字段；
5. 数据源异常不会直接写数据库。

### Job 测试

1. 成功任务状态流转正确；
2. 失败任务状态流转正确；
3. 任务记录包含采集数量；
4. 已成功任务可以跳过；
5. 历史回补单日失败不会中断全部任务。

### Repository 测试

1. 行情批量写入成功；
2. 重复数据不会产生重复行；
3. 写入失败可以回滚；
4. 任务状态可以正常更新；
5. 失败任务可以正确查询。

### 集成测试

```text
调用数据源
    ↓
生成统一数据
    ↓
写入 MySQL
    ↓
更新任务状态
    ↓
检查最终数据
```

## 14. 开发步骤

### 第一步：梳理现有采集代码

检查：

```text
data_loader/collector.py
data_loader/tushare_api.py
database/
config/
```

找出数据源调用、数据库写入、清洗、日志、异常处理及与其他模块之间的依赖。

### 第二步：建立独立服务目录

新建：

```text
services/python-collector/
```

先建立目录和空模块，不急于迁移全部代码。

### 第三步：抽取 Collector

要求：

```text
输入采集参数
输出统一格式数据
不直接写数据库
```

### 第四步：抽取 Repository

要求：

```text
只处理数据库读写
不调用外部接口
不控制采集流程
```

### 第五步：建立 Job

使用 Job 串联任务状态、Collector、数据检查、Repository、日志和异常处理。

### 第六步：增加任务状态表

创建 `collection_task`，实现任务创建、更新和失败查询。

### 第七步：增加重试机制

仅对可恢复异常进行有限次数重试。

### 第八步：增加命令行入口

支持单日采集、历史回补、基础信息更新和失败任务重试。

### 第九步：双入口验证

迁移期间同时保留：

```text
旧采集入口
新 python-collector 入口
```

使用相同日期的数据进行对比。

### 第十步：停止旧采集入口

新采集服务稳定后：

1. Dashboard 不再触发采集；
2. 模型训练不再触发采集；
3. 原 `data_loader` 中旧采集入口标记为废弃；
4. 所有采集任务统一通过 `python-collector` 运行。

## 15. 数据对账

新旧采集流程需要使用同一交易日进行对账。

建议检查：

```text
总行数
股票代码数量
最大交易日期
空值数量
重复数量
开盘价合计
收盘价合计
成交量合计
成交额合计
```

还需随机抽样若干股票，对比：

```text
open
high
low
close
pre_close
pct_chg
volume
amount
```

只有对账通过，才能停止旧采集入口。

## 16. V0.2 验收标准

V0.2 完成后应满足以下条件：

1. 采集服务可以独立启动；
2. 不启动 Dashboard 也能采集数据；
3. 不训练模型也能采集数据；
4. 支持指定交易日采集；
5. 支持指定日期范围历史回补；
6. 支持失败任务重新执行；
7. 数据源调用与数据库写入完全分离；
8. Tushare 和 AkShare 具有统一接口；
9. 采集任务状态可以查询；
10. 重复采集不会产生无效重复行情；
11. 采集异常有完整日志；
12. 原有特征、模型和页面功能不受影响；
13. 新旧采集结果完成数据对账；
14. 新采集入口稳定后，旧入口停止使用。

```text
Java Flink
  ↓
ClickHouse
```

重点是实时清洗和 DWD 数据落库。

因此，V0.2 是后续大数据架构的基础版本。只有先明确采集服务的职责，V0.3 才能以较小改动将 MySQL 输出替换或扩展为 Kafka 输出。

## 19. 实习项目描述

> 将原有股票分析系统中的数据采集模块拆分为独立 Python 服务，抽象 Tushare 和 AkShare 多数据源统一采集接口，实现按交易日采集、历史数据回补、失败任务重试和任务状态追踪。将数据源调用、任务编排与数据库访问进行分层，利用业务唯一键保证行情写入幂等，为后续 Kafka 消息化和 Flink 实时处理改造提供基础。
